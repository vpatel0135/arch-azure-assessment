# Assumptions and design decisions

| Area | Assumption / decision and reason |
| --- | --- |
| Scope | One new resource group in one supplied subscription. Application code, real secret values, documents and employee sign-in implementation are outside this infrastructure exercise. |
| Region and SKUs | `eastus2` by default, configurable. Linux P1v3 supports VNet integration/private endpoints; Standard LRS Storage keeps the example simple. Confirm regional .NET 10 availability before deployment. |
| Network | A configurable non-overlapping IPv4 /16 provides separate /24 integration and private endpoint subnets (`10.42.1.0/24` and `10.42.2.0/24` by default). Separation accommodates App Service subnet delegation. |
| Employee access | Corporate VPN/ExpressRoute or peering and private DNS forwarding already exist. They must provide routes to this VNet; they are not created by this stack. Private networking does not replace employee authentication. |
| DNS and monitoring | Dedicated application VNet/DNS scope. An inbound App Service endpoint is included for employee access. Azure Monitor Private Link Scope provides private telemetry; its five DNS zones reuse the application Blob zone. Shared enterprise monitoring DNS would require integration review. |
| Common identity | One user-assigned managed identity belongs to the Web App and is reused for Vault, Blob and telemetry. Target services authorize this caller; they do not each need a separate identity to accept requests. The eventual app uses the supplied client ID and service URLs with managed-identity SDK authentication. |
| Data permissions | Secrets User is scoped to the Vault, Blob Data Contributor to the documents container, and Monitoring Metrics Publisher to Insights. No account keys or passwords are passed in app settings. Key Vault reference identity selection is also configured. |
| Telemetry interpretation | Application telemetry goes through workspace-based Insights; resource diagnostics go directly to its backing workspace, matching Section 7. Diagnostic delivery uses Azure's private service channel. Insights local-key ingestion authentication and public ingestion/query are disabled. Only Azure-supported diagnostic categories are exported. |
| Groups and PIM | Both enterprise groups already exist and their object IDs are inputs. Appropriate PIM licensing is available. Writers receive 90-day eligibility, with MFA, justification and four-hour maximum activation. Approval was not requested, so no approval stage is added. The fixed start timestamp avoids eligibility changing on every run; expiry requires deliberate renewal. |
| Naming and tags | `<abbreviation>-<environment>-<workload>` names use a stable subscription/workload hash where global uniqueness is required; Storage/Vault names are shortened to Azure limits. Descriptive child names identify the integration/endpoint subnets and documents container. Tags identify environment, application, owner, cost center and Terraform. |
| Retention | Log retention is 30 days; Key Vault soft deletion is 90 days with purge protection. A deleted Vault cannot be immediately purged or its name reused. These explicit retention choices favor simple operations and recoverability. |
| Provisioning | AzureRM Storage data-plane checks are disabled; AzAPI creates the container through ARM. No queue/static-website features are used. Infrastructure creation uses management APIs; using private service endpoints afterwards requires private connectivity. |
| Prerequisites | Subscription resource providers are registered externally. The deployer has resource creation, unrestricted role-assignment, eligibility-schedule and role-management-policy permissions. Reader/Contributor alone cannot configure all governance resources. |
| State and validation | Local state for the isolated exercise; production would use secured remote state. Actual tfvars, state and plans are excluded from Git. Validation is static/CI, with an apply description rather than a live Azure plan; no deployment or runtime/idempotency test is claimed. |
